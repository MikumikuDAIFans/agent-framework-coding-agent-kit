# 外部来源审核机制

## 文档状态

- Policy ID: `AF-CAK-EXTERNAL-SOURCE-REVIEW`
- Version: `v1.0`
- Policy owner: `project maintainer`
- Last updated: `2026-07-15 Asia/Shanghai`
- Approval status: `approved`
- Effective from: `2026-07-15`
- Supersedes: `draft-0`

本政策用于决定外部资料能否成为 coding agent 的 Microsoft Agent Framework（MAF）开发参考。
它不评价资料的知名度，而评价资料能否提供可信、当前、可落地的设计与实现证据。

## 1. 适用范围与分轨

候选来源分成两条审核轨道：

1. **项目与代码轨**：官方或社区代码仓库、可运行示例、模板和完整应用。
2. **文档与技术文章轨**：官方工程博客、社区技术文章和带代码的教程。

以下内容不进入正式审核：Issue、Discussion、问答与论坛内容，视频、课程、演示文稿和
Awesome list。它们只能帮助发现原始来源，不能进入正式主题索引，也不能作为 API 或设计证据。

`official-doc`（Microsoft Learn 与 Microsoft 官方 API 文档）适用第 5 节的直接入选规则，
不参与文章评分。Microsoft 官方工程博客仍按“文档与技术文章轨”评分。

## 2. 统一评分方法

每个维度先按证据评为 `0–5` 级，再按权重换算：

```text
维度得分 = 维度权重 × 证据等级 ÷ 5
总分 = 各维度得分之和（满分 100）
```

只允许使用整数等级。没有证据时计 `0`，不得凭印象补分。

| 等级 | 通用含义 |
| ---: | --- |
| 0 | 不存在、无法核实，或证据与声明相反 |
| 1 | 只有声明、零散片段或非常弱的证据 |
| 2 | 有初步证据，但不完整、不可复现或依赖较强假设 |
| 3 | 有清晰证据，达到可用基线，适用边界可说明 |
| 4 | 证据完整且可复现，明确处理重要工程边界 |
| 5 | 高质量、系统化、可跨项目复用，并有强验证证据 |

最终审核必须同时记录等级、换算分数和证据位置。总分不能覆盖第 6 节的硬门禁。

## 3. 项目与代码轨（100 分）

| ID | 维度 | 权重 | 重点证据 |
| --- | --- | ---: | --- |
| C-01 | 设计价值 | 25 | 架构边界、状态与数据流、取舍、可复用模式、失败处理 |
| C-02 | 测试和验证 | 25 | 可重复命令、单元/集成/eval、CI、失败用例、真实运行证据 |
| C-03 | 生产化深度 | 20 | 安全、身份、可靠性、可观测性、部署、扩缩容、回滚 |
| C-04 | 真实 MAF 依赖 | 10 | manifest/import、包版本、实际调用、构建或运行结果 |
| C-05 | 来源与作者可信度 | 10 | 所有者身份、技术履历、署名、许可证、声明与代码一致性 |
| C-06 | 版本可追溯性 | 5 | commit/tag/release、lock 文件、运行时和 Provider 坐标 |
| C-07 | 维护活跃度 | 5 | 近期有效提交、Issue/PR 响应、发布节奏、是否归档 |

评分细则：

- **设计价值**：`0` 无可识别设计；`3` 有可复用结构并说明主要边界；`5` 对架构、取舍、
  失败与适用范围形成系统性参考。
- **测试和验证**：`0` 无验证；`3` 有可运行的自动化测试或 eval；`5` 有 CI、分层测试、
  失败样本与可重复环境。
- **生产化深度**：`0` 纯玩具；`3` 覆盖若干关键生产边界；`5` 同时具备安全、可靠性、
  可观测性、部署和回滚闭环。
- **真实 MAF 依赖**：`0` 未使用 MAF；`3` 有直接依赖、明确版本和代表性 API 调用；`5`
  依赖完全锁定且已构建或运行验证。
- **来源与作者可信度**：`0` 身份/来源可疑；`3` 来源、署名和许可证清楚；`5` 有持续、
  可核实的相关工程产出，且声明与实现一致。
- **版本可追溯性**：`0` 只有移动分支或未固定依赖；`3` 可定位 commit 和主要依赖；`5`
  可重建完整依赖与运行环境。
- **维护活跃度**：`0` 已归档或明显失维护；`3` 近 12 个月有实质维护；`5` 近 3 个月持续
  维护并及时处理兼容性问题。新但高质量的稳定项目不得仅因提交频率低而降到 `0`。

## 4. 文档与技术文章轨（100 分）

| ID | 维度 | 权重 | 重点证据 |
| --- | --- | ---: | --- |
| A-01 | 是否有真实 Demo | 30 | 可访问代码、依赖、运行步骤、输入输出、复现结果 |
| A-02 | 设计价值 | 25 | 非空谈的设计决策、取舍、边界、失败经验和复用价值 |
| A-03 | 技术新颖程度 | 15 | 与当前 MAF API/能力一致，正确标注 preview/deprecated 状态 |
| A-04 | 文章发布日期 | 15 | 首次发布日期、最近实质更新日期及变更说明 |
| A-05 | 来源与作者可信度 | 15 | 作者身份、相关经验、引用质量、披露和技术准确性 |

评分细则：

- **真实 Demo**：`0` 无代码；`1` 仅伪代码、截图或无法定位的片段；`2` 有不完整代码；
  `3` 有可访问 Demo、依赖和运行步骤；`4` 依赖已固定且结果可核实；`5` 已由审核者复现并有测试。
- **设计价值**：`0` 只有概念或营销描述；`3` 用 Demo 解释关键设计和适用边界；`5` 提供
  系统性取舍、失败分析和可迁移设计。
- **技术新颖程度**：`0` 主要 API 已移除或废弃；`1` 明显过时；`2` 与当前版本存在重要偏差；
  `3` 与当前受支持 API 一致；`4` 覆盖当前新能力且成熟度标注准确；`5` 对最新能力有官方或源码验证。
- **文章发布日期**（以审核日为基准）：3 个月内 `5`；3–6 个月 `4`；6–12 个月 `3`；
  12–18 个月 `2`；18–24 个月 `1`；超过 24 个月 `0`。只有包含技术内容变更的更新才重置日期，
  仅修改排版或时间戳不算。
- **来源与作者可信度**：`0` 身份或内容来源可疑；`3` 作者可核实、引用可追踪且与 Demo 一致；
  `5` 作者在相关领域有持续产出，关键声明均能被官方文档、源码或运行结果交叉验证。

## 5. 官方文档直接入选

`official-doc` 不计分，完成以下快照后直接标记为 `adopted`：

- 记录规范 URL、页面标题、抓取/审核日期和适用语言；
- 标注目标 MAF 包/API 版本及 `preview`、`experimental`、`deprecated` 状态；
- 与本地上游源码、公开 API 或测试进行一次冲突检查；
- 记录页面漂移、语言版本差异和已知实现缺口。

直接入选表示它是最高优先级文档证据，不表示其中所有示例都已通过生产验证。若官方页面与
目标版本冲突，应保留来源但标记版本边界；已撤回或被替代的页面进入 `quarantined`，并链接替代页。

## 6. 硬门禁

以下条件不能用高总分抵消：

- 项目/代码没有可核实的直接 MAF 依赖或实际 API 调用：`rejected`。
- 技术文章的真实 Demo 等级低于 `3`：`rejected`。
- 技术文章的主要 API 已移除、已废弃，或无法映射到当前目标版本：`rejected`。
- 技术文章超过 24 个月且没有可核实的实质更新：`rejected`。
- 泄露凭据、恶意指令、伪造运行结果或严重误导性声明：`rejected`；存在尚未确认的严重风险时先
  `quarantined`。
- 代码许可证缺失或不允许预期复用：不得 `adopted`；在许可证澄清前为 `quarantined`。
- 无法给出 commit/tag/page date 等可追溯坐标：不得 `adopted`。

## 7. 分数与状态

| 条件 | 状态 | coding agent 允许用途 |
| --- | --- | --- |
| 官方文档完成第 5 节快照 | `adopted` | 文档/API 证据，必须携带版本边界 |
| 评分来源总分 `>= 80` 且通过全部硬门禁 | `adopted` | 可作为设计与实现参考；仍需注明版本、语言和限制 |
| 总分 `65–79.99` 且通过硬门禁 | `context-only` | 只用于背景、设计启发或反例，不作为 API 正确性证明 |
| 总分 `50–64.99`，或存在可修复的证据缺口 | `quarantined` | 不向 coding agent 推荐，等待补证或复审 |
| 总分 `< 50` 或触发拒绝型硬门禁 | `rejected` | 仅保留拒绝原因，不进入知识索引 |

工作流状态：`discovered` 表示仅发现；`queued` 表示等待审核；`in-review` 表示正在收集证据。
只有 `adopted` 可以提议加入 `topics.json`，且索引晋升必须是独立、可审查的变更。

## 8. 单来源审核最低记录

每份 `reviews/<source-id>.md` 必须包含：

- 来源类别、规范 URL、作者/所有者、许可证和不可变坐标；
- 适用语言、MAF 包/API 版本、Provider、运行时和成熟度；
- 与本地上游源码、测试和官方文档的对照；
- 对应轨道的逐维等级、分数、证据和总分；
- 已执行与未执行的验证、示例捷径、生产化缺口和安全风险；
- 硬门禁检查、最终状态、允许/禁止用途和再审核触发器。

审核者可以收集事实和提出结论；最终 `adopted` 状态及 `topics.json` 晋升由项目维护者批准。

## 9. 再审核与自动化

出现下列任一情况必须重新审核：目标 MAF 大版本变化；来源默认分支、release 或依赖坐标变化；
文章满 12 个月；仓库连续 12 个月无实质维护；许可证变化；发现安全问题、错误 API 或失效链接。

自动化可以校验权重总和、字段完整性、唯一性、HTTPS、状态、审核文件存在性和分数计算；不得
代替证据判断、自动批准 `adopted`，也不得自动晋升 `topics.json`。
